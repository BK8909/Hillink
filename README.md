# HILLINK

### 후기 기반 가상 고객 행동·소비·호텔 운영 전략 시뮬레이터

> **“같은 고객이 다른 날, 다른 조건으로 호텔을 방문한다면 어떤 선택을 할까?”**
>
> HILLINK는 실제 이용 후기에서 고객의 경험과 선택 기준을 추출하고, 새로운 호텔 방문을 가상으로 실행해 **고객 행동·소비·운영 전략을 함께 탐색하는 시뮬레이터**입니다.

> **연구·기술 인계:** 설계 근거, 규칙·LLM 정책 구분, 페르소나 추출 구조, 평가 지표와 과거 실험의 한계는 [hillink/docs/research/RESEARCH_AND_ARCHITECTURE_HANDOFF.md](hillink/docs/research/RESEARCH_AND_ARCHITECTURE_HANDOFF.md)에 정리했습니다.

호텔의 실제 매출을 예측하거나 고객의 미래 선택을 맞혔다고 주장하는 서비스는 아닙니다. **관측된 후기 근거와 명시한 가상 조건을 바탕으로, 어떤 선택이 가능하고 운영 개입에 따라 무엇이 달라질 수 있는지 설명하고 실험하는 것**이 목표입니다.

## 1. 문제와 목표

호텔 운영자는 이벤트, 할인, 레스토랑 메뉴, 패키지, 운영 시간처럼 다양한 조건을 바꿀 수 있습니다. 그러나 이런 조정이 서로 다른 고객의 실제 동선과 소비에 어떤 영향을 주는지는 사전에 실험하기 어렵습니다.

같은 커플 여행객이라도 누군가는 미식 경험을, 누군가는 전망과 휴식을, 또 다른 누군가는 포함 혜택과 편리한 동선을 우선합니다. HILLINK는 이런 차이를 단순한 고객 유형 하나로 환원하지 않고, **각 고객이 실제로 남긴 경험과 그때의 맥락**에 연결하고자 합니다.

운영자는 가상 호텔의 조건을 바꾸고 고객들의 선택을 관찰한 뒤, 특정 업장으로 유치하거나 기존 소비를 바꾸는 전략을 비교할 수 있습니다. 즉, 호텔 운영을 작은 시뮬레이션 환경처럼 실험하되 고객의 행동에는 설명 가능한 근거와 실행 제약이 따라붙도록 만드는 것입니다.

## 2. 연구 접근 — 후기에서 행동으로

### 고객 프로필을 어떻게 만드는가

1. **원문 수집:** 워커힐 방문기뿐 아니라 같은 작성자의 다른 호텔·여행·다이닝 경험과 최근 글도 함께 살핍니다.
2. **Fact 추출:** 이용한 장소·식사·메뉴·동행·시간·평가·구매 여부 등을 출처 구간과 연결합니다.
3. **사건 단위 정리:** 동일 방문을 여러 글에서 언급했다면 중복 경험으로 세지 않습니다. 작성자와 동행인의 경험도 구분합니다.
4. **선택 기준 해석:** 반복되는 선호, 가격·혜택 판단, 공간과 분위기, 편의, 실패·후회 경험 및 반례를 정리합니다.
5. **기준 사례 검증:** 행동이 풍부한 실제 방문을 관측 사례로 사용하고, 아직 일어나지 않은 다른 계절·행사·일정은 별도의 반사실적 상황으로 시험합니다.

후기에 언급이 없다고 방문하지 않았거나 싫어했다고 판단하지 않습니다. **관측 사실, 프로필 추론, 운영자 가정, 가상 실행 결과**는 구분해서 다룹니다.

### 사람의 하루처럼 이어지는 의사결정

고객은 매 순간 독립적으로 가장 높은 점수의 장소만 고르지 않습니다. 이전에 무엇을 먹었는지, 얼마나 쉬었는지, 동행인이 누구인지, 예약과 영업시간이 어떻게 남아 있는지, 내일 다시 기회가 있는지에 따라 계획을 바꿀 수 있습니다.

이를 위해 HILLINK는 다음 요소를 연결합니다.

- **고객 기억과 상태:** 후기에서 추출한 성향, 이번 방문의 식사·활동, 허기·피로 등의 모델 상태, 목표와 남은 일정
- **행동 판단:** 가능한 후보와 이후 일정까지 고려해 행동을 선택하는 자율 LLM 정책 및 비교 가능한 규칙 정책
- **운영 검증:** 이동·대기·영업시간·예약·이용 자격·가격·상품 구성·중복 식사 등 호텔 운영 제약
- **실행 결과:** 실제 채택된 선택을 장면·주문·상품·가상 거래 원장에 연결
- **독립 평가:** 선택의 근거가 원문 Fact와 맞는지, 기억과 시간 관계가 타당한지, 불확실성을 숨기지 않았는지 검토

중요한 원칙은 **LLM이 선택한 뒤 그럴듯한 이유를 붙이는 것이 아니라, 선택 이전에 어떤 판단과 대안을 고려했는지 검증 가능한 기록으로 남기는 것**입니다.

## 3. HILLINK의 주요 기능

### ① 고객 라이브러리와 프로필

고객 유형별 카드에서 개인 프로필, 방문 경험, 선택 기준, 연결된 후기 원문과 Fact를 살펴볼 수 있습니다. 같은 유형이라도 실제 관측된 행동과 추론된 성향은 구분합니다.

### ② 방문 조건 설정과 고객 행동 실행

고객 한 명 또는 여러 명을 선택해 다음 조건을 조정합니다.

- 비투숙 당일 방문부터 1박 2일·2박 3일·3박 4일
- 방문일, 도착 시간, 등록된 행사와 날씨 가정
- 투숙 건물·동행·조식·객실 패키지 등 지원되는 이용 조건
- 규칙 계산, 동일 입력의 저장 LLM 응답 재현, 승인된 환경에서의 새로운 LLM 판단

가상 고객이 식사·산책·휴식·행사·객실 이용 등을 선택하면 운영 엔진이 실행 가능성과 상품 계약을 검증합니다. **각 실행의 판단 출처는 명확히 표시하며, LLM 응답이 없을 때 규칙 선택을 LLM 결과로 위장하지 않습니다.**

### ③ 고객 흐름과 행동근거

기존 지도와 장면을 따라 하루를 수동으로 재생하며, 고객이 언제 어디에서 무엇을 선택했는지 확인합니다. 행동근거에서는 실제로 주어진 상황, 연결된 개인 Fact, 비교한 대안, 선택 이유, 운영 규칙 검증과 최종 주문을 같은 실행에서 역추적할 수 있습니다.

화면 속 고객의 말은 가상 실행에 대한 설명이지 실제 고객의 발언이 아닙니다.

### ④ 가상 주문과 호텔 매출 집계

선택된 상품의 SKU·수량·금액을 가상 원장에 연결합니다.

```text
L5 고객별 거래
 ↓
L4 상품별 주문·소비
 ↓
L3 업장별 합계
 ↓
L2 부문별 합계
 ↓
L1 호텔 전체 가상 소비
```

객실, 식음, 레저/시설 소비를 함께 살펴볼 수 있고, 포함 혜택·할인·가정 요금·가격 미확인을 구분합니다. **가상 결제액은 호텔의 실제 POS 매출, 영업이익 또는 미래 매출 예측이 아닙니다.**

## 4. 운영 전략 — 고객을 어떻게 유치하고 소비를 변화시킬까?

HILLINK의 운영 전략은 단순히 추천 문구를 만드는 기능이 아닙니다. **고객의 실제 가상 선택을 읽고, 호텔 운영자가 조절할 수 있는 조건을 찾아 다시 실험하는 과정**입니다.

### 목표 설정 → 진단 → 전략 → A/B → 결론

**1. 운영 목표를 정합니다.**  
예를 들어 더뷔페 고객 유치, 피자힐 메뉴 구성과 소비 개선, 호텔 외부 배달 수요의 내부 전환, 특정 행사 참여 확대 또는 호텔 전체 가상 소비를 목표로 삼습니다.

**2. 현재 고객 선택을 진단합니다.**  
고객이 어디에서 무엇을 선택했는지, 목표 업장이 선택 가능한 후보였는지, 비선택 이유에 가격·시간·이동·예약·상품 구성이 실제로 기록되어 있는지를 확인합니다. 목표 업장이 후보에 없었다면 없는 이유를 추측으로 만들지 않습니다.

**3. 고객별 운영 가설을 제시합니다.**  
후기 Fact와 반례, 이번 방문의 동선을 기반으로 미식·새 경험, 음식 취향, 혜택 활용, 공간·분위기, 예약·편의, 가격 대비 가치 등 관점에서 접근합니다. 같은 업장을 유치하더라도 고객마다 다른 개입이 필요할 수 있습니다. 개인별 제안을 모아 고객군 차이와 공통 전략도 살펴봅니다.

**4. 실행 가능한 개입을 A/B로 비교합니다.**  
운영자가 조정할 수 있고 상품·가격·시간·자격 계약이 확인된 조건만 실제 가상 재계산에 연결합니다. 새로운 메뉴나 행사 아이디어가 아직 엔진의 후보와 원장에 없다면 **미실험 가설**로 둡니다.

**5. 변화의 의미를 구분합니다.**  
목표 SKU 선택, 목표 업장 이용, 같은 업장 내 메뉴 교체, 기존 고객 할인 비용, 부문별 소비, 호텔 전체 소비를 나누어 봅니다. 목표 업장 유입이 0명이면 그대로 0명으로 보고하고, 다른 업장에서 발생한 지출 변화를 할인 효과로 잘못 귀속하지 않습니다.

**예시 — 피자힐에서 저녁을 선택한 고객을 더뷔페로 유도할 수 있을까?**

우선 피자힐 선택의 근거와 더뷔페의 후보 포함 여부를 확인합니다. 그 고객이 미식 경험을 중요하게 보는지, 일정·가격·영업시간이 장애인지 구분한 뒤 가능한 운영 변수를 변경합니다. 실제로 선택이 바뀌지 않았다면 이를 가설의 실패 또는 미변화로 기록합니다. **할인율을 설정했다는 사실만으로 고객이 이동했다고 계산하지 않습니다.**

운영 전략의 결과는 세 단계로 읽어야 합니다.

| 단계 | 의미 |
|---|---|
| 고객 근거에 기반한 전략 제안 | 실험할 가치가 있는 가설 |
| 조건 변경 후 가상 A/B 비교 | 특정 실행에서 관찰한 행동·소비 차이 |
| 호텔에서의 실제 운영 효과 | 실제 예약·매출·고객 반응으로 추가 검증할 별도 과제 |

현재 제품은 고객별/집단별 전략 검토와 제한된 가격·시간 조건 비교를 지원합니다. 모든 전략 제안이 즉시 실행 가능한 것은 아니며, **실제 운영 성과나 인과효과가 자동으로 확정되지는 않습니다.**

## 5. 현재 구현 범위와 남은 과제

현재 제품에는 **고객 프로필·원문 근거, 연속 방문 시뮬레이션, 자율 LLM 행동 결정과 운영 검증, 상품 주문·가상 매출, 운영 목표 및 개인·집단 전략 비교**를 위한 코드와 데이터가 구현되어 있습니다.

여러 고객을 대상으로 실제 모델 행동 판단을 실행하고, 판단·주문·원장의 연결 및 독립 평가를 수행했습니다. 일반 방문에서도 규칙/정확한 저장 응답 재현/새로운 LLM 판단을 구분하는 실행 경로를 제공합니다. 새로운 모델 호출은 키·사용량 승인·예산 설정이 있는 환경에서만 사용합니다.

다음 항목은 제품과 연구를 확장하면서 계속 검토해야 합니다.

- 후기에 기록된 의미와 프로필 해석의 정확성, 서로 다른 글과 사건의 연결
- 개인 Fact가 실제 선택에 기여한 정도, 약한 선호 전이와 반례 처리
- 연속 식사·휴식, 동행 구성, 허기·피로, 예약·이용 자격에 대한 현실성
- 공식 메뉴·가격·판매 조건과 실제 운영 정책의 지속적인 대조
- 전체 고객군의 전략 효과와 실제 수요·매출·인과효과 검증

**기술적으로 실행할 수 있다는 사실은 고객 행동의 현실성이나 운영 효과가 입증되었다는 뜻이 아닙니다.** 기존의 실험·평가 결과와 미해결 계약은 개발자 검수 자료로 보존합니다.

## 6. 설치와 실행

**권장 환경:** Python 3.11, macOS 또는 Linux, 웹 브라우저. JavaScript 검수를 수행하려면 Node.js가 필요합니다.

저장소를 내려받은 뒤 현행 제품 폴더 `hillink/`에서 실행합니다. 기존 팀 파일을 복사하거나 조합할 필요가 없습니다.

```bash
cd hillink
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
bash tools/start_product.sh
```

기본 주소는 [http://127.0.0.1:8994/](http://127.0.0.1:8994/)입니다. 사용 중인 포트는 `HILLINK_PORT` 환경변수로 변경할 수 있습니다.

기본 실행은 외부 API 호출 없이 규칙 계산과 **입력 조건이 정확히 일치하는 기존 LLM 응답 재현**을 사용할 수 있도록 합니다. 새로운 LLM 판단이 필요한 경우 승인된 키·기존 비용 원장을 갖춘 환경에서 `bash tools/start_product.sh --live`로 실행합니다. 응답이 일치하지 않으면 다른 고객의 응답을 대신 사용하지 않습니다.

실행에 필요한 승인 범위의 샘플 입력·원문·메뉴·실험 자료는 프로젝트 패키지에서 무결성을 검사해 복원합니다. API 키와 인증정보는 포함하지 않습니다. 후기 원문·고객 자료·이미지의 재배포 권한은 별도로 확인해야 합니다.

### 페르소나를 새로 추가하려면

`원문 준비 → LLM 추출 결과 생성 → 원문 인용·사건·Fact 검증 → 사람 검수 → 격리 등록 → 새 방문 실행`의 순서로 진행합니다.

`tools/persona_pipeline.py`가 준비·수입·승인·등록·검증의 단일 진입점을 제공합니다. 현재 이 CLI는 직접 모델을 호출하기보다는 승인된 LLM 환경에서 생성한 결과를 받아 검사합니다. 사람 검수가 끝나지 않은 프로필을 자동 등록하지 않습니다.
