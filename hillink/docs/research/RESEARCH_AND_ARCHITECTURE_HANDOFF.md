# HILLINK | 연구·기술 아키텍처 및 검증 기록

> **기준:** 2026-11-07 공개 제품 최신 버전  
> **내용:** 연구 배경 · 시스템 아키텍처 · 구현·검증 결과 · 남은 연구·개발 과정

이 문서는 HILLINK의 설계 근거와 실제 구현·연구 결과를 추적할 수 있도록 정리한 기술 기록이다. 설명의 기준은 **검증 가능한 코드·로그·입력 조건**이며, 기술적 실행 성공과 행동 타당성 또는 미래 예측 정확도를 구분한다. 제품 설치·복원 방법은 [README](../../../README.md)와 [RECOVERY.md](../../handover/RECOVERY.md)를 참조한다.

**공개 범위:** 이 문서에는 후기 원문, 개인 식별 정보, API 키, 비공개 응답 전문, 접근 권한이 불분명한 이미지 등을 포함하지 않는다. 문서의 공개 가능성과 저장소 안의 모든 데이터 재배포 가능성은 별개다.

## 0. 기술 개요

HILLINK는 실제 고객 후기에서 관측한 경험과 선택 근거를 바탕으로, **아직 일어나지 않은 워커힐 방문을 가상으로 실행하고**, 그 선택이 어떤 상품·주문·가상 매출로 이어지며 운영 조건을 바꾸면 무엇이 달라지는지 추적하는 시뮬레이터다. 실제 매출 예측기나 검증된 디지털 트윈이 아니다.

| 차원 | 하는 일 | 핵심 코드 |
|---|---|---|
| 1D 고객 이해 | 같은 작성자의 워커힐 후기·다른 호텔·식음·최근 글을 묶어 Fact(원문 구간 연결)와 성향 가설을 만든다 | `author_method_v4_1/` · `author_validation_v4_2/` · `tools/persona_pipeline.py` |
| 2D 연속 방문 | 시각·위치·끼니·허기·피로·동행·예약·행사 상태에서 가능한 행동을 만들고, 규칙 / 선택적 LLM / 자율 LLM(V16·V17) / V19LS(M4 후보 선별 + LLM 선택, 11/07부터 기본 LIVE)로 선택·검증한다. V18은 같은 구조의 연구 계열이다 | `autonomy_v1/agent_day.py` · `m4_runtime.py` · `autonomous_agent.py` · `m4_shortlist.py` |
| 3D 소비·운영 | 실제 실행된 SKU·수량을 같은 run의 L5 → L1 가상 원장으로 집계하고, 운영 전략 가설과 서버가 허용한 A/B만 비교한다 | `timeline/viewer/ledger_service.py` · `strategy_agent.py` · `strategy_agent_service.py` |

현재 공개 제품에는 결정 주제별 개인 근거·반례와 중립적인 후보 제시를 결합한 **V19LS 실시간 판단 정책**을 기본 LIVE로 반영했다. 규칙 엔진은 실행 가능한 행동·판매 상품·가격·수량·이용 제약을 관리하고, LLM은 그 안에서 개인 경험과 현재 방문 상태를 고려해 행동을 선택한다. 최종 선택은 기존 월드·상품·원장 계약을 다시 통과해야 실행된다. 과거 V17의 복수 계획 자율 판단 경로와 정확 입력 V16 Replay는 보존된다. 실시간 AI 기능은 별도의 승인된 호출 환경이 필요하다.

**연구 이력 안내:** 11월 6일의 LS 미승격은 당시 실험 결과이고, 현재 공개 제품에는 개선·검증을 거친 V19LS가 기본 실시간 판단 정책으로 적용되어 있다. 각 시점의 실험 조건과 결과는 아래 연구 이력에 구분해 보존한다.

**이전 연구·검증 기록 (2026-11-06 기준, 당시 상태)**
- 라이브러리 45명 표시 · 실행 가능 28명 / 열람 전용 17명. 대표 문구 45명은 선정 원문 사례로 대조했고, blog42·blog43은 원문 연결 HOLD. **45명 전체의 의미·썸네일 사람 승인은 아님.**
- V16 실호출 검수 기록: 28명 · 완료 36방문 · 312판단(LIVE 301 / Replay 11) · 실패 시도 2건 보존. 이 문서를 쓰며 다시 실행하지 않았다.
- 2026-11-06 V18 교차 실험: `gpt-6-luna` / `medium`으로 **실제 호출 224회**, 단일 판단 144건의 첫 시도 계약 검증 **144/144**, 전체 방문 9건 중 7건 완주·2건 호출 상한 중단, 9건의 실행된 주문과 가상 매출 원장 일치. 이는 **실험 성공과 계약 정합성**이며 미래 행동 정확도가 아니다.
- LS(L2 결정 주제별 개인 근거 + S2 중립 제시)는 24개 결정 시점에서 무과금 입력·계약 점검을 통과한 뒤, 2026-11-06 V17과 같은 5개 진단 사례에서 **실제 호출 16회(정책별 8회)**로 비교했다. LS는 지연(평균 13.3초 vs 45.3초)과 비용(US$0.0104 vs US$0.0589)이 낮았으나, V17 대비 개인 근거 전달의 개선은 관측되지 않았고 이유와 선택이 어긋난 사례 1건이 있어 **제품에 승격하지 않았다**(5-7절). 11/06 제출 제품은 V17 LIVE 기본 + V16 Replay였다(11/07 V19LS 승격은 5-8절).
- 과거 개발용 평가 수치(F1·Brier 등)는 **규칙 기반 v4 시절의 개발 자료 안 탐색 평가**이며, 현재 V16/V17/V18의 행동 예측 성능이 아니다.
- **평가 방법과 후속 연구 설계를 혼동하지 않는다.** 10/27의 100점 근거 평가 루브릭 및 10/28의 실증 행동 prior·의도/계획 모델은 연구 설계 기록이며 현재 V16의 검증된 성능이나 구현 기능을 뜻하지 않는다(5-4, 9-2절).

## 1. 연구 문제 정의와 설계 전환

| 시기 | 그때의 질문 | 드러난 한계 → 다음 선택 |
|---|---|---|
| 9월 | 후기에 적힌 방문 장소를 에이전트가 재현하는가 | 장소 일치만으로는 매장/포장, 예약, 결제, 선택 이유를 평가할 수 없었다. 검증기(운영 규칙)를 먼저 통과한 행동만 고르는 구조로 위반을 막았다 |
| 9월 말 ~ 10월 초 | 고객군이 어디서 얼마나 소비하는가 | 수요 규모·좌석·비투숙 배율 같은 가정이 매출을 크게 바꿨다. 확정·추정·미확인 값을 나누고, 운영 수치보다 근거 사슬에 집중하기로 했다 |
| 10월 중순 | 성향이 행동을 설명하는가 | 개발 자료에서 성향의 추가 설명력이 확인되지 않았다(5절 E0·E2). 후기 한 편으로는 지속 성향과 일시 조건을 가르기 어려워 **작성자 단위 프로파일링**으로 확대했다 |
| 10월 말 ~ 11월 초 | 새 행사·가격·상품 조건에서 같은 고객이 어떻게 행동하고 소비하는가 | 점수의 사후 설명으로는 부족했다. **선택 이전에** 상태·대안·기억·반례를 보고 고르게 하고, 그 선택을 소비·전략 입력까지 같은 run으로 잇는 구조(V16/V17)로 옮겼다 |
| 11월 6일 | 개인 근거와 상황을 어떻게 질문에 넣으면 결정이 달라지는가 | 동일 고객·후보의 **근거 선별(C/L2)**과 **후보 중립 제시(S2)**를 분리 비교하고, 근거 누락·기념일 해석·반복 대기·식사량 공백을 별개 결함으로 식별했다. 결합 정책 LS는 구조 검증 후 V17과 실호출로 비교했고, 승격하지 않았다 |
| 11월 7일 | 어떻게 그 사람다운 판단을 유지하면서 실시간 사용 속도를 높일 것인가 | 기존 LS의 혼합 평가·선택 이유 불일치와 하루 종료 재검토 오류를 진단했다. 근거의 긍정·부정·조건부 의미, 후보 관련성, 선택-이유 진단, 대안 비교 검증을 강화한 V19LS를 구현·실측했고, 공개 제품의 기본 LIVE로 적용했다(5-8절) |

설계 목표는 개인의 미래 행동을 맞혔다고 증명하는 것이 아니라, **근거가 있는 그럴듯한 선택을 재현하고 그 판단과 집계를 감사할 수 있게 만드는 것**이다. 실제 운영 효과 검증에는 POS·예약·수요·재고 같은 현장 자료와 별도 대조군이 필요하다.

**연구 품질 게이트(10/27~29 의사결정 기록):** 실험을 새로 시작할 때는 `운영 질문 → 실제로 관측한 행동 품질 결함 → 수정할 프로필/추출기/엔진 → 결정·방문에서 확인할 변화 → 실패 시 중단·역추적 조건`을 먼저 명시한다. 반복 시드 수·에이전트 수·점수 상승 자체가 목적이 아니다. 연구 기록에서 이 원칙을 `NORTH_STAR_V1`, `METRIC_DRIFT / STOP_AND_REDIRECT`로 관리했다. 다만 해당 명칭은 **연구 수행 원칙**이지 런타임 정책 상수나 이미 실행된 검사 결과가 아니다.

## 2. 규칙 엔진 — 설계 근거와 한계

### 2-1. 왜 규칙 엔진부터 만들었나

1. **운영 규칙 위반을 구조적으로 막기 위해.** 에이전트는 매 턴 검증기를 통과한 행동만 후보로 받는다. 위반 0은 점수가 아니라 전제 조건이다(아무 데도 가지 않아도 위반은 0이다).
2. **설명이 계산과 일치하게 하기 위해.** 동결 정량 엔진은 점수를 `특성 수준 × 선택지 속성 × 역할 계수` 항의 합으로 만들고 항마다 근거 Fact ID를 붙인다. 이유 문장은 실제로 계산에 들어간 항에서만 만든다([engine.py](../../timeline/experiments/persona_live/operator_choice/operator_world_v1/engine.py) 머리말).
3. **재현성과 무과금 대조군.** 같은 시드면 같은 하루가 나오고 호출 비용이 없다. 이후 LLM 정책을 평가할 때 비교 기준이 된다.

### 2-2. 계수를 어떻게 다뤘나

- `W`(novelty 2.0 · food 3.0 · cost 2.0 · rest 2.0 …)는 **초기 가설**이다. 엔진 주석에 "특정 고객·조건의 결과에 맞춰 조정하지 않음"이 명시돼 있다. 점수는 효용 지표이지 확률·지불 의사·학습된 계수가 아니다.
- 비용 항은 개인의 가격 회피 성향이 아니라 공통 상황 판단(`COST_ATTENTION 0.5`, 5만 원 단위)이다.
- 정책 스위치(`fact_share` · `lookahead` · `lookahead_depth 2` 등)는 모든 고객에게 같은 규칙으로 적용하고, 비교 실행은 정책을 바꿔 같은 입력으로 다시 돌린다.
- 이 구조의 이론적 배경은 **효용 기반 이산 선택**(McFadden 1974, Train 2009 — 중간보고서·최종보고서 인용)이다. 다만 HILLINK가 로짓 계수를 추정해 확정한 것은 과거 v4 연구(5절 E0)뿐이며, 현재 엔진의 `W`는 추정치가 아니다.

### 2-3. 한 번의 결정 (규칙 실행기)

[agent_day.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/agent_day.py) 머리말의 7단계: ① 상태 읽기 ② 욕구·의무 판단(체크인·체크아웃·끼니 창·피로) ③ 그 시각 가능한 후보 생성 ④ 월드 규칙 검증(영업시간·투숙객/성인 전용·계절·행사·운영자 변경) ⑤ 개인 평가(엔진 지원 상품은 동결 정량 엔진, 그 밖은 계획기 성향 가중치·시드 고정) ⑥ 실행·상태 갱신 ⑦ 운영 변경 뒤 결정부터 새 월드로 재판단.

현재 실행 경로는 [m4_runtime.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/m4_runtime.py)(`m4-live-v2-shared-world`)가 공유 월드와 시간순 결정 큐로 묶는다. 설정값에 `capacity_and_queues_supported: False`가 명시돼 있다 — **좌석·대기·정원 경쟁은 모델링하지 않는다**(프로젝트 범위 결정).

[docs/walkerhill-guest-state-machine.md](../walkerhill-guest-state-machine.md)는 2026-09-20 작성된 **상태 모델 설계 초안**(transition/guard 미정의)이다. 초기 월드 설계의 참고 자료이지 현재 런타임이 아니다.

### 2-4. 알려진 한계

- 성향 항의 기여가 작아, 고른 후보에 개인 근거가 붙지 않는 결정이 생긴다(아래 선택적 검토의 `NO_PERSONAL_BASIS` 트리거가 이를 감지하려고 만든 것).
- 엔진이 지원하지 않는 활동(점심·카페·라운지 등)은 계획기의 성향 가중치로 고르며 정량 근거가 약하다.
- 과거 v4에서 예약 가점이 업장 단위로 붙어 포장 후보에도 적용되던 구조 한계가 기록돼 있다(10/18 읽기 점검). 현재 엔진에서의 재확인은 하지 않았다.

## 3. 행동 결정 계층 — 규칙·선택적 검토·자율 LLM·V18 연구·V19LS

| 정책 계열 | 최종 선택의 주체 | 구현·적용 범위 | 검증·해석의 경계 |
|---|---|---|---|
| 규칙 (`judgment_mode=rules`) | 규칙 엔진 | 후보와 상태를 점수·시드·운영 제약으로 계산 | 무과금 기준선. 점수는 행동 확률이 아님 |
| 선택적 LLM 검토 `SELECTIVE_V12Z_NATIVE_V1` / `CLAUDE_HYBRID_REVIEW_V1` | 규칙이 먼저 결정, 지정 순간에 LLM 검토 | 조건부 호출·`adopt` / `shadow` | LLM이 호출되지 않은 결정을 LLM 성과로 세지 않음 |

### 3-1. 선택적 검토의 트리거 ([hybrid_review.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/hybrid_review.py))

`NEAR_TIE`(상위 두 후보 점수 차 < 0.35) · `COST_ABSTAIN`(가격 미확인으로 금전 항 제외) · `REPEAT_VENUE` · `REPEAT_MENU` · `NO_PERSONAL_BASIS`(고른 후보에 개인 근거 항 없음) · `PRICE_GAP`(가격 민감 근거가 있는 고객이 최저가의 2배 이상 선택). 그 밖의 결정은 호출 0이다. 이 설계는 "계수로 재기 자연스러운 판단은 규칙이, 근거가 부족하거나 추론이 필요한 순간만 LLM이"라는 10/29 하이브리드 원칙을 구현한 것이다.

### 3-2. V16 계약 ([autonomous_agent.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/autonomous_agent.py))

- `configuration()`: `selector='LLM_FINAL_INTENT'` · `validator='M4_C01_CONTRACTS'` · `fallback='EXECUTION_HOLD_NO_SCORED_SUBSTITUTION'` · `max_replans=1` · 기억 정책 `LLM_VISIT_MEMORY_V3` · 월드 `AUTONOMOUS_WORLD_CONTRACTS_V4` · 끼니 `AUTONOMOUS_MEAL_EXPERIENCE_V5`.
- 출력 스키마: `plans`(1~5개) + `selected_index`. 계획마다 `action_id` · `items[{sku_id, quantity 1~32}]` · `order_total_krw` · `supporting_fact_ids` · `counterevidence_fact_ids` · `assumptions` · `pending_intentions` · `current_need_assessment` · `meal_assessment` 등.
- 검증(`validate_plan`): 검증된 월드 밖 행동, 입력에 없거나 인용 불가한 Fact, 일정 충돌, 체크인 전 객실 이용, 활동의 고정 주문 변경, 식사 무주문, 최근 같은 업장 재식사, SKU 중복·미판매·수량 범위, 주문 총액 불일치, 포함 혜택·가격 계약 위반을 거절한다.
- 실패 흐름(`step`): 검증 거절 → 거절 사유를 붙여 **한 번만** 재계획 → 다시 실패하면 `REPLAN_VALIDATION_EXHAUSTED`. provider 실패(`ProviderUnavailable`)는 즉시 `EXECUTION_HOLD`. 후보가 없으면 `NO_VALIDATED_ACTIONS`. **어떤 경우에도 규칙 점수로 몰래 대체하지 않는다**(`selection_owner=None`, `price_score_rerank=False`).
- 로그: 후보 수와 ID, 제외 사유, `input_sha256`, `implementation_sha256`(소스 해시), `profile_evidence_sha256`, 시도별 provider 기록, 선택 계획, 실행 전후 상태.
- 시스템 지시에 "점수 엔진의 추천은 없습니다", "기록된 끼니가 없다는 것을 굶었다는 사실로 해석하지 마세요", "null 가격은 미확인이며 무료가 아닙니다" 등 과잉 해석 금지가 들어 있다.

이전 연구 문서나 `agent_day.py`의 옛 주석에 나오는 규칙 폴백 설명과 V16 동작이 다르면 **현행 코드가 우선**이다.

### 3-3. 왜 V16으로 옮겼나 (설계 기록)

규칙 엔진은 위반이 없고 재현 가능했지만, 개발 평가에서 성향이 행동을 설명하는 몫을 입증하지 못했고(5절), 연속된 하루에서 이전 식사·기억·남은 일정·메뉴 수량을 함께 판단하는 데 한계가 있었다. 선택적 검토는 규칙의 불확실 지점만 보완한다. V16은 **선택은 LLM이, 실행 가능성은 기존 월드 계약이** 맡도록 역할을 나눈 것이다. 이 전환이 행동 예측 정확도를 높였다는 독립 평가는 **없다**.

### 3-4. LIVE / Replay / 규칙의 증거 수준 ([agent_provider.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/agent_provider.py) · [visit_execution.py](../../timeline/viewer/visit_execution.py))

| 실행 출처 | 뜻 | 성능 근거로 쓸 수 있나 |
|---|---|---|

### 3-5. V18 후보 선별과 LLM 질문의 역할 분리

V16/V17은 LLM이 여러 계획·메뉴를 구성하는 반면, V18은 규칙 엔진(M4)이 **현재 실행 가능한 3~5개 행동과 상품·수량·가격 계약**을 먼저 만든 뒤 LLM에 그 안에서 하나를 고르게 한다. 결정을 받아들일 때는 기존 전체 월드·SKU·원장 검증을 그대로 적용한다. 즉 모델에게 더 적은 범위를 제시하는 것이며, 모델 선택을 규칙 점수의 최상위 후보로 강제하는 설계는 아니다.

연구 비교에서 중요한 것은 모델 이름만이 아니라 **요청의 실제 구성**이다. 고객의 개인 Fact, 상충 경험, 동행과 방문 목적, 직전 식사·허기·피로, 남은 일정, 선택 가능한 업장과 메뉴, 후보 제시 순서, 스키마와 추론 강도를 입력 해시와 함께 보존한다. 선택이 달라졌을 때 근거 검색 누락과 모델 해석 문제를 혼동하지 않도록 한다.

| 연구 정책 | 바뀐 요인 | 결과 판정 범위 |
|---|---|---|
| C (`V18BM`) | 후보 관련 개인 근거 + 기존 표시 방식, `medium` | LIVE 비교 기준 |
| L2 (`V18L2`) | 결정 주제별 개인 근거·경량 문맥 | LIVE 비교, 효율·근거 전달 개선 관측 |
| S2 (`V18S2`) | 점수/가격 순위 유래 표현 제거, 종류·이름순 중립 제시 | LIVE 비교, 표시 유도 완화 관측 |
| LS (`V18LS`) | **L2 근거 + S2 중립 제시** | **24개 시점 요청 동등성·합성 방문 계약 검증 후 V17과 LIVE 비교(16호출); 제품 미승격** |

**현재 구조(2026-11-07):** V16/V17은 LLM이 여러 계획과 메뉴 수량을 구성한다. V19LS는 M4가 실행 가능한 후보와 판매 단위·수량·가격을 먼저 고정하고, LLM이 근거·반례·현재 상태를 검토해 한 선택을 반환한다. **V19LS에서 선택 주체는 LLM이며, 후보 타당성과 최종 실행 주체는 규칙·운영 검증 계층**이다. 점수 최고 후보를 무조건 선택하는 방식이 아니다. V19LS의 근거 성격 표시는 자동 단서 추출이므로 사람이 승인한 감정 라벨과 구분하며 요약의 원문 문구를 우선한다.

관련 구현: [autonomous_agent.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/autonomous_agent.py), [ls_stability.py](../../timeline/experiments/persona_live/operator_choice/autonomy_v1/ls_stability.py), `tools/v18_bench/{driver,run,request_diff,evidence_check}.py`, `tools/v18_batch/batch.py`. 연구 경로는 제출 패키지 구성에 따라 접근이 제한될 수 있으며, 코드 경로는 통합된 제품 레이아웃의 `hillink/` 기준이다. 공개 저장소 반영 시 실제 상대 경로를 검증한다.

### 3-6. 근거의 존재와 근거의 전달을 구분

후기에서 추출된 Fact가 원본에 **존재**하더라도, 특정 행동 후보와 연결하는 검색·필터가 그 Fact를 모델 입력에서 **제외**하면 선택 시 이를 활용할 수 없다. V18에서 C/S2는 출처 범위가 워커힐로 확인된 `source_scope='wh'` 업장명만 후보 근거로 연결하도록 만들어져, 출처가 `UNRESOLVED`인 고유 업장명을 일부 누락했다. L2/LS의 결정 주제 선별은 해당 누락을 피했다(5-6절).

개선 방향은 **고유 업장명**(피자힐·명월관 등)과 **일반 서비스명**(룸서비스 등)을 구별하는 것이다. 고유 업장명이 명시됐고 타 호텔 경험으로 확인되지 않았으면 관련 기록을 보존하되 `출처 미확인`을 함께 전달한다. 단, **관련성 ≠ 호감·실제 이용**이며 혼합·부정 평가를 긍정 성향으로 변환하지 않는다. 이 연결 정책의 C/S2 적용은 `f0ab802` 기준 **제안 상태**다.

## 4. 페르소나 추출 — V4.1과 V4.2

### 4-1. 왜 작성자 단위인가

워커힐 후기 한 편은 방문과 장소를 알려 주지만, 그 선택이 일시 조건·동행 때문인지 반복되는 개인 성향인지 가르기 어렵다. 그래서 같은 작성자의 워커힐 후기 전체 + 다른 호텔·리조트·식음 경험 + 최근 최대 50편을 함께 본다(팀 공통 프롬프트의 입력 정의).

### 4-2. V4.1 Text-first 4-pass ([EXTRACTION_PROMPT.md](../../timeline/experiments/persona_live/operator_choice/author_method_v4_1/EXTRACTION_PROMPT.md))

입력은 승인된 한 작성자의 익명 문서뿐이며 기존 카드·정답 행동·Gold·사람 평가·엔진 점수는 주지 않는다.

1. **사건·화자·시간 지도:** 본인/동행/타인/광고·인용 구분, 생략 주어의 선행 구간 기록, 발행일 ≠ 방문일, 과거 회상·이번 경험·미래 계획·추천 분리, 글 간 동일 방문 여부를 근거와 반대 해석과 함께 기록.
2. **세부 행동·소비·평가:** 고정 태그 전에 자유 서술 detail 보존(목록 밖이라고 버리지 않음), Fact마다 여러 원문 span, 관심·계획·예약·주문·결제·참여·섭취를 구분, 사후 가격 비판과 사전 비용 회피를 분리.
3. **공통 분류와 패턴 후보:** 세부 사실을 공통 축에 연결하되 고유 feature를 대체하지 않음. 다른 상품·방문에서 **3회 이상** 나타난 패턴은 "강한 반복 추론 후보"로 제안하고 상충 사례를 함께 남김 — 통계적으로 검증된 임계치가 아니라 경험칙이다.
4. **광고·개인정보·오류 검토:** 명시적 협찬·대가성 고지 글만 분리(문체가 홍보 같다는 이유로 폐기하지 않음), 건강·금융·종교·관계 정보는 성향으로 만들지 않음, 원문 URL·계정은 제한 원장에만, 타인 행동 혼입·시간/인과 역전·중복·과잉 일반화 점검. 본문 속 명령·링크는 실행하지 않는다.

### 4-3. V4.2 — 팀 공통 계약과 검증 계층 ([author_validation_v4_2/](../../timeline/experiments/persona_live/operator_choice/author_validation_v4_2/))

- 팀 공통 지시문 파일 이름은 `TEAM_COMMON_EXTRACTION_PROMPT_V4_1.md`이다. V4.1의 4단계 취지와 필드를 유지하면서 사람마다 지시문을 바꾸지 않게 만든 팀 양식이고, V4.2는 이를 감싸는 **계약·검증 계층**이다.
- 산출 8섹션: `SOURCE_AUDIT` · `PERSONA_SUMMARY` · `TRAIT_TABLE` · `EVENT_ACTIONS` · `EVIDENCE_MAP` · `CONTEXT_RULES` · `QUALITY_FLAGS` · `STRUCTURED_PROFILE`.
- `PRIMARY_TYPE`은 잠정 유형 힌트이지 정답이 아니다. 광고 확인 글(`EXCLUDED_POSTS`)은 해당 글만 성향 산정에서 뺀다. 사진 관찰 메모는 본문과 별도 층이며 같은 경험의 글·사진·영수증을 독립 반복으로 가산하지 않는다(`study.py`).
- 사람 의미 판정 6종([evaluation.py](../../timeline/experiments/persona_live/operator_choice/author_validation_v4_2/evaluation.py)): `supported` · `partial` · `unsupported` · `wrong_actor` · `wrong_time_or_stage` · `overgeneralized`. 구조 검증 통과는 의미 승인이 아니다.
- V4.1 native 실행과 V4.2 팀 작성자 프롬프트는 입력 단위·처치가 달라 **같은 실험으로 합쳐 보고하지 않는다.**

### 4-4. 누출 방지와 새 작성자 추가

- 추출 요청에는 개발 라벨·어휘 후보·옛 카드·행동 선택·평가자 의견을 넣지 않는다(`study.py` 머리말). 새 작성자는 `author_role='holdout_new_author'`로 준비한다.
- [tools/persona_pipeline.py](../../tools/persona_pipeline.py)는 `prepare → (승인된 외부 LLM에서 별도 추출) → import → 사람 approve → register → verify` 인터페이스이며 **스스로 LLM을 호출하지 않는다**("External inference is never run by this tool"). 등록은 내장 등록부 17명에 새 고객을 더한 **격리 등록부**를 만들 뿐 기존 28명을 덮어쓰지 않는다. 절차는 [handover/persona/README.md](../../handover/persona/README.md).
- 예제 A14는 저장된 초안의 재수입이며 모델 실행 이력이 없어 새 LLM 추출로 인증하지 않는다. 사람 검수 대기라 `approve`·`register`는 차단 상태다.

### 4-5. 원문 → 성향 → 후보 선택의 양방향 피드백(연구 방법론, 제품 자동화와 구분)

추출 품질은 단순히 `Fact` 수나 프로필 문장이 자연스러운지로 평가하지 않는다. **같은 작성자의 독립된 경험·주체·행동 단계**를 먼저 만들고, 성향 가설이 **선택 이전**에 실제 후보·판단에 사용됐는지를 역추적한다. 10/27 `PERSONA_METHOD_SPEC_V1`, 행동 이유 평가·역설계 프로토콜은 다음 절차를 제안했다.

1. 해당 고객의 **실행 전** 프로필/Fact 버전, 가능한 후보, 사용한 특성·계수, 선택/비선택과 L5 원장을 고정한다.
2. 본인 프로필 / 성향 중립 / 타인 프로필 / trait 제거의 대조를 동일한 월드·시나리오·시드 또는 짝 시드에서 비교한다. **선택이 달라졌다는 사실과 그 선택이 타당하다는 판단은 별개**다.
3. 오류 원인을 `wrong_actor`, `wrong_time_or_stage`, `trait_action_mapping`, `candidate_missing`, `world_constraint`, `rationale_fabrication` 등으로 분류한다.
4. 근거 부족이 실제 추출 누락 때문이라면 **기존에 허용된 동일 작성자 원문**에서 직접·간접·부정 단서와 방문 맥락을 다시 추출한다. 이미 시뮬레이션한 결과 자체를 새로운 고객 Fact로 만들지 않는다.
5. `trait_value`(해석 방향·강도 가설), `evidence_strength`(근거 수준), `episodic_context_match`(상황 적합성), 출처·반례·독립 사건 수를 분리해 기록하고 같은 조건에서 재실행한다.
6. 최종 선택뿐 아니라 상위 후보·결정 경계·연속 동선·SKU·원장·악화 사례까지 비교해 `ADOPT / IMPROVE / HOLD / REJECT`를 기록한다.

이 경로의 일부 국소 실험 기록은 남아 있으나, 위 여섯 단계 전체가 모든 고객에게 자동화·사람 승인·독립 평가되었다는 자료는 없다. 연구 원문의 공개 범위는 기술 요약과 별도로 감사한다.

### 5-4. 행동 이유 평가 — 두 종류의 평가를 분리(10/27 **설계 규약**, 미승인 점수체계)

| 평가 경로 | 물음 | 데이터 경계 | 결과를 해석할 때의 제한 |
|---|---|---|---|
| **관측 행동 held-out** | 계수 조정에 쓰지 않은 **작성자의 별도 봉인 방문 행동**을 재현하는가? | 작성자·방문/사건 단위 분리, 평가 대상 선택·원문 정답의 추출 입력 누출 금지, 중복 기사·후기를 독립 사례로 세지 않음 | `top1`, rank/MRR, 근거 연결 등을 평가할 수 있으나 후기의 미기재는 미방문 증거가 아님 |
| **반사실적 방문의 grounded plausibility** | 실제 일어나지 않은 방문에서 고객다운 선택·대안·연속 동선이 납득되는가? | 모델명/실험군을 숨긴 평가, 관측 Fact·추론·시나리오 가정 구분, 결정 **이전** trace 검사 | 특정 미래 행동의 정답·예측 정확도가 아닌 구조화된 사람 검수·반례 분석 |

10/27 연구 프로토콜은 **근거 연결 35 / 선택 이유의 계산상 연계 25 / 월드·상황 적합 20 / 개인 특이성 10 / 대안 비교 10 = 100점**의 *잠정 루브릭*을 제안했다. 사람 2인 평정·점수 보정·독립 검증을 마쳐 공식 지표로 승인한 결과는 **없다**. LLM이 자기 답을 스스로 채점해 높은 점수를 얻은 결과를 독립 평가로 취급하지 않는다. 월드 위반은 별도 실행 FAIL, 원문이 없는 개인화 근거는 그 행동의 개인화 근거 점수를 0으로 처리한다는 설계 원칙이다. 이 100점 규약을 최신 제품 V16의 36회 독립 평가 기록과 동일한 평가기로 합산하지 않는다.

사람/자동 검수에 필요한 최소 필드(제안): `customer_id`(비식별) · `author_split` · `source/profile/world/policy_sha` · `event_visit_id` · `decision_id` · `pre_state` · `feasible_candidates` · `choice` · `supporting/counterevidence_fact_ids` · `selection_owner` · `predecision_contributions` · `LLM origin` · `alternative_reasons` · `unknowns` · `L5-L1 refs` · `reviewer/verdict`. **출처가 실제로 사용됐는지** 확인하려면 설명 카드에 Fact ID를 적는 것만으로는 부족하며, 결정 경계의 제거·교환 실험까지 구분해야 한다.

### 6-3. 아직 적용하지 않은 행동학·의도 연구의 문헌 경계

10/28 M4-BPI(Behavioral Priors & Intentions) 별도 설계는 **실제 참여 기회의 분모를 가진 행동 기본률**, **개인 후기의 잔차**, **목표와 의도 유지·재검토**를 결합하자는 방향을 제시했다. 구현된 실증 계수표나 HILLINK 고객 행동 확률이 확인된 상태는 아니다.

- *계획·의도 효과*: Gollwitzer & Sheeran (2006), implementation intentions 관련 문헌은 **계획이 행동에 미치는 효과**를 검토할 출발점이다. 논문 `d≈0.65` 같은 효과크기를 `계획 유지 확률 65%`로 변환하지 않는다. [DOI](https://doi.org/10.1016/S0065-2601(06)38002-1).
- *다양성 추구·포만, 활동 재참여*: 같은 식당 재방문과 동일 행사 반복을 같은 감점으로 묶지 않고 `activity × opportunity × visit`별로 분리해 관측하도록 설계했다. 인용 문헌의 모집단·시간 범위를 호텔 1~3박에 바로 이전할 수 없다.
- *계획 재고려*: 사건으로 **반드시** 바꿔야 하는 예약/운영 제약과, 개인이 **선택적으로** 재고려하는 계획을 분리한다. 계획 변경 확률의 분모는 매 분/모든 결정이 아니라 실제 `eligible_reconsideration_event`다.

위 문헌·모형은 **향후 연구 참고**이며, 현행 `agent_experience.py`의 기억·`pending_intentions` 존재를 실증된 재참여율이나 BDI·POMDP 구현 증거로 사용하지 않는다. 자세한 비교 구조와 검증 요구는 9-2절에 둔다.


BDI·POMDP·강화학습 같은 이론을 구현 근거로 사후에 덧붙이지 않는다. 논문의 지표 이름이 같아도 문제와 자료가 다르면 같은 점수로 취급하지 않는다.

## 7. 소비 원장과 운영 전략 — 제안과 실행의 경계

- **원장:** [ledger_service.py](../../timeline/viewer/ledger_service.py)(`live-l5-v2`)가 실행된 영수증을 L4 → L1로 조립하고 `receipts_equal_L4_L3_L2_L1`을 확인한다. 외부 배달 같은 호텔 밖 지출은 L1에 넣지 않고 금액 미상으로 따로 표시한다.
- **전략 입력:** [strategy_agent_service.py](../../timeline/viewer/strategy_agent_service.py)는 서버가 발급한 run만 받는다("never accept client Fact/flow data"). run이 만료되면 `SERVER_RUN_EXPIRED_REEXECUTE_REQUIRED`, 원본 run이 다르면 `SOURCE_RUN_MISMATCH`.
- **전략 가설:** [strategy_agent.py](../../timeline/viewer/strategy_agent.py)(`LLM_OPERATOR_STRATEGY_V3`)는 6종(experience·food·benefit·space·convenience·value)으로 운영 가설을 낸다. Fact를 고치거나 구매를 만들거나 매출 증가를 추정하지 않으며, 미선택 이유는 `RECORDED_COMPARISON` / `HYPOTHESIS` / `NO_EVIDENCE`로 구분한다. 모델은 스스로 실행 가능한 개입을 승인할 수 없고, 서버가 검증한 실험 계약이 있을 때만 `AVAILABLE_NOT_RUN`, 없으면 `UNTESTED_HYPOTHESIS_ENGINE_CONNECTION_REQUIRED`다.
- **A/B 결과 해석:** 목표 업장 신규 유입, 기존 고객 주문 구성 변화, 다른 업장 감소, 할인 비용, 호텔 L1 차이를 나눠 본다. 변화 0, 실험 불가, Replay 실패, 근거 부족을 구분한다. 현장 POS·대조군 없는 값은 **가상 소비 변화**다.

**전략 해석 사례:** 피자힐로 유입된 고객이 생겨도 다른 호텔 업장 소비가 줄었다면 호텔 전체 가상 순증은 별개다. 동일 업장 내 저렴한 메뉴로의 전환은 매출 잠식일 수 있다. A/B 결과표에는 `실제 실행된 개입/가설만 존재/Replay 실패`, `신규 유입/동일 고객 주문 변경/다른 업장 이탈`, `목표 업장 변화/호텔 L1 변화`, `상품 가격 근거/미확인 금액`을 모두 병기한다. 미검증 정책의 숫자를 실제 운영 성과로 해석하지 않는다.

## 9. 남은 연구·개발 과정

이 절은 미완성 기능을 이미 구현된 성과처럼 나열하지 않기 위한 **연구·개발 로드맵**이다. 선행 검증 없이 복수 요인을 한 번에 바꾸지 않으며, 각 단계는 `문제 → 입력 변경 → 비교 기준 → 실측 결과 → 악화 사례 → 채택/보류`로 기록한다.

### 9-1. P0 — 행동 판단 입력·정책 검증(완료 성과와 남은 항목)

1. **정책 비교 및 승격 완료:** 11월 6일 LS와 V17의 실제 비교(16호출)를 거쳐, 11월 7일 개선 정책 V19LS의 실호출 130회·대표 고객 비교·예외 재검증을 수행했다. 그 결과 V19LS를 기본 실시간 판단 정책으로 적용했다(5-8절). 남은 과제는 신규 고객·시나리오에서의 개인 행동 품질 검증, A05 식사량, 일부 조식 후보 구성 및 응답 지연 개선이다.
2. **근거 연결 보존:** 후보 이름이 등장하는 기록에서 출처가 `UNRESOLVED`여도 고유 업장명을 보존할지 별도 정책으로 시험한다. 미확인 출처는 표시하고, 고유명과 범용 서비스명을 분리한다. 긍정·부정·혼합 판단은 별도 사실로 남긴다.
3. **현재 방문 목적과 과거 사례 구분:** ‘과거 기념식사를 했다고 이번에도 기념일이라 가정하지 말 것’과 ‘운영자가 이번 방문을 기념일로 설정한 사실’이 충돌하지 않도록 지시를 구분해 실험한다. 기념일 문구를 억지로 출력하게 만드는 것이 아니라 **선택 내용·상품 수준·근거의 적합성**을 평가한다.
4. **A19형 식사량 환산 공백:** 메뉴별 `meal_equivalents`가 미표시인 상태를 0/소식으로 간주하지 않도록 자료 정의를 보강하거나 `미확인`을 명시하는 대조 실험을 한다.
5. **반복 대기·일정 재검토:** 대기를 일률적으로 금지하지 않는다. 직전 대기 이유와 그사이 바뀐 상태, 다음 행동 가능한 시점, 남은 일정의 기회비용을 제공해 동일 이유의 반복을 줄이는지 검증한다.

**승격 게이트:** 개인 근거 전달·선택 자연스러움·상황 적응·다양성·중대한 월드 위반·HOLD·매출 정합성·비용·시간을 모두 살피고, 악화 사례가 있으면 수정 정책만 보류한다. 검증을 거치지 않은 정책을 제품 기본값으로 설정하지 않는다.

### 9-2. P1 — 독립 평가체계와 페르소나 품질

- **관측 행동 held-out:** 동일 작성자의 본문 중 프로필 구축에 활용되지 않은 방문/사건을 작성자·사건 단위로 봉인한다. 정답 누출, 시점 뒤집힘, 중복 관측을 먼저 차단하고 장소·행동·근거·시간·단계별 일치를 측정한다. 후기 미기재는 미방문의 증거가 아니다.
- **반사실적 개연성:** 미래에 실제 발생하지 않은 방문에 정답 행동을 부여하지 않고, 원문 근거·동행·상태·운영 가능성·대안 비교·연속 방문의 일관성을 모델명·정책명 가림 후 사람이 평가한다. LLM 자기평가와 독립 사람 평정을 섞지 않는다.
- **페르소나 의미 감사:** 45명 카드 노출과 28명 기술 실행을 의미 승인으로 혼동하지 않는다. blog42·43의 원문 연결 HOLD, 동일 사건·화자 귀속, 광고·인용 구분, 789행 의미 대조 등 남은 검수 항목을 재현 가능한 증거와 함께 정리한다.
- **기여도 역추적:** 같은 후보·월드를 고정한 상태에서 본인 프로필·성향 중립·타인 프로필·Fact 제거를 비교한다. 단순히 선택이 바뀌었다는 사실은 개인화의 개선을 의미하지 않는다. 모델 호출·평가 비용을 별도 기록한다.

### 9-3. P2 — 연속 방문 계획과 행동 기저 모형

2026-10-28에 설계한 **M4-BPI(Behavioral Priors & Intentions)**는 실증 기본률·상황 조정·개인 기록의 잔차와 **목표/의도 유지·재검토**를 연결하는 장기 연구안이다. 2026-11-06의 제품 코드에서 실증 기본률 표나 완성된 의도 확률 모델이 검증되었다고 보지 않는다: `DESIGNED / NOT_IMPLEMENTED / NOT_VALIDATED`.

| 가상 연구 단계 | 가설·모형 | 필요한 증거 |
|---|---|---|
| A0 | 규칙 M4 기준선과 V17 자율 선택 기준선 | 고정 고객·후보·시드·월드·정책 SHA |
| A1 | 실증 행동 사전확률(`prior_registry`) | 참여 가능 기회(`eligible_opportunity`)의 분모, 모수·표본·기간·신뢰구간. 임의 확률 사용 금지 |
| A2 | 욕구(`desire`) / 의도(`intention`) / 확정 예약 / 실제 가상 실행 구분 | 관심 보류(`DEFERRED`)와 비선호·불가능·미확인을 구분한 사건 기록 |
| A3 | 당일·익일 짧은 계획과 사건 기반 재검토 | 운영 변경, 식사·피로, 행사 시작, 남은 시간 등 실제 재검토 사건과 반례 |
| A4 | 의미 충돌 지점의 제한적 LLM 비교 | 규칙/LLM 분담의 품질·시간·비용·대기 악화 여부에 대한 대조 실험 |

예컨대 늦은 점심과 수영 뒤 저녁을 고를 때, 관측된 일식 선호·동행·피로·식욕·이동 거리와 다음 날 행사 기회가 함께 주어진다면 **오늘의 선택과 보류할 계획**을 동시에 다루는 것이 연구 목표다. 특정 음식점이나 행사를 미리 정답으로 지정하지 않으며, 사실로 확인되지 않은 동행 취향·예약 조건을 추가하지 않는다.

### 9-4. P3 — 운영 실험의 외적 타당성

- 행사/날씨/상품/가격 중 **한 변수만** 조정해 같은 run 기반 가상 A/B를 재현한다. 업장 유입·업장 내 메뉴 이동·기존 고객 할인 비용·타 업장 이탈·호텔 전체 L1 변화를 분리한다.
- 제안만 있고 실제 후보·상품 계약에 연결되지 않은 전략은 `UNTESTED_HYPOTHESIS`로 기록한다. 실행 불가·미선택·근거 부족·가격 미확인은 서로 다른 상태다.
- POS·예약·실제 이용 자격·재고·좌석·시즌 가격·현장 서비스 정책이 확보되지 않으면 실제 전환율·매출 증가·인과효과로 일반화하지 않는다.

### 9-5. 반복 가능한 최소 검증 절차

1. 고정 코드 SHA·고객·날짜·시드·정책으로 승인된 방문 Replay를 실행하고 동일 입력이 아니면 `REPLAY_MISS`를 기록한다.
2. 한 run 안에서 **고객 Fact → 후보·배제 사유 → 선택·대안 → SKU/수량 → L5~L1 → 운영 전략 입력**을 왕복 추적한다.
3. 독립 승인된 자료 또는 합성 예제로 신규 프로필 `prepare → import → 사람 approve → register → verify`의 단계별 차단을 확인한다.
4. 단일 변경을 적용한 재실험에서 계약 위반 0, 원장 일치, 비용·호출 기록, 행동 품질 악화 여부를 각각 보고한다.
5. 연구 결과를 제품에 반영할 때는 회귀 테스트와 제품 실행 검수 후 **채택/보류/기각 근거**를 함께 남긴다.

## 10. 공개 자료와 비공개 연구 자료의 경계

이 문서는 공개 가능한 **기술 구조·집계된 실험 사실·제약 및 방법론**을 서술한다. 사용 권한을 보유한 자료라도 공개 재배포가 허용된 자료인지는 별도로 판단한다.

| 자료 유형 | 공개 기록에 포함 가능한 형태 | 별도 검토가 필요한 부분 |
|---|---|---|
| 개인 후기·Fact | 익명화된 Fact ID, 출처 확인 상태, 집계된 테스트 결과 | 원문 전문, 글 링크·계정, 재식별 가능한 인용문, 개인 기호와 민감정보 |
| 모델 입력·응답 | 정책 이름, 설정, 입력 SHA, 선택 라벨, 비용·지연 통계 | 비공개 개인 근거가 들어간 요청·응답 원문 |
| 이미지·호텔 자료 | 권리가 확인된 샘플과 구조 설명 | 공식 사진, 로고, 메뉴 이미지, 인물·생성 이미지의 사용 조건 |
| 코드·실험 결과 | 공개 허용된 구현, 익명화된 비교 요약, 테스트 절차 | 로컬 전용 연결표, 비공개 원장, 라이선스 불명 자료가 섞인 번들 |
| 인증·비용 | 환경변수 예시, 예산 가드 구조 | 실제 키, 토큰, 로컬 키 파일, 개인 결제·원장 상세 |

**검증 가능한 기술 자료와 배포 가능한 데이터는 동일하지 않다.** 공개 패키지를 구성할 때 파일별 출처·라이선스·식별 가능성·의존 관계·SHA를 감사하고, 저장소에서 비공개 자료를 단순 삭제해도 과거 Git 기록에 남는지 확인한다. 공개 패키지의 내용과 별도로 승인된 비공개 연구 원본은 권한을 분리해 보관한다.
